# REA 下一阶段逆向任务书：为生产 RAG 补齐版本与证据

> 公开入库适配：原文结论和历史验证范围保留；本机路径与原包链接改为本目录投影。原件摘要见 SOURCE-DOCUMENTS.json。此副本不包含原始战报/截图，也不是新的逆向、模型调用或知识发布记录。

日期：2026-10-18
目标项目：Sanmou / 《三国：谋定天下》QA Agent
文档性质：任务方向与验收建议，不代表任务已经执行或证据已经补齐。

## 1. 总目标

为版本感知、证据约束的游戏知识 RAG Agent 补齐三类信息：

1. **适用性**：资料来自哪份资源，适用于哪个版本、剧本、实体变体和具体条件。
2. **解释能力**：冲突数值、单位、概率与显示规则分别意味着什么。
3. **证据边界**：哪些是配置、客户端说明、限定战报/UI观察，哪些仍是推断或未知。

本轮不以恢复完整战斗引擎、全部服务器公式或任意战报自动采集为目标。优先完成能直接改善问答准确性、来源引用和拒答质量的小范围闭环。

需要保留的边界：

- 旧选样文档写“清醒碰撞缺样本”，后续已补一个UI个例。新任务应基于最新增量，而不是重复旧问题。

## 4. REA-R01：版本、剧本与实体变体映射

### 要回答的问题

- 10月13日静态快照与后续1.37快照中，哪些记录、字段和引用发生变化？
- Scenario如何选择？配置加载、覆盖和回退的顺序是什么？
- 同名武将、隐藏记录、NPC、特殊版本如何区分？
- 显示/外放字段能证明什么，哪些不能证明当前赛季可招募或服务器生效？
- 某个知识条目同时依赖多个资源时，如何记录这些依赖，而不伪造一个统一版本？

### 最小范围

先覆盖RAG首批18类代表性样本，再根据差异风险扩展。不要把“全量重提所有资料”作为首批交付的前置条件。

### 交付物

- 资源快照清单：文件身份、SHA256、客户端build（若可确认）、保存时间与来源。
- 稳定ID对应的字段级差异表，区分新增、删除、值变化和引用变化。
- 实体映射：namespace、source ID、变体、快照、Scenario；中文名只作为展示/别名。
- 配置选择与覆盖路径，附实际函数、表行或Evidence ID。
- 无法确认的适用范围和未知项清单。

### 验收与停止条件

- 样本内每个结论都能追溯到指定快照和实体。
- 不以采集日期代替游戏版本，不把未知适用范围解释为所有版本适用。
- 静态调用关系与实际运行观察分别标记。
- 如果只能证明客户端选择路径，无法确认服务器覆盖，则在此边界停止并记录未知；不无限扩大到服务器引擎。

## 5. REA-R02：19条缘分冲突的字段消费路径

### 优先案例

1. “三分天下”：客户端文案6%，平行字段0.05。
2. “虎卫御侮”：文案与平行字段涉及不同效果语义，不能仅做百分比换算。

### 分析方法

逐项追踪：原始表行 → 字段读取函数 → 转换/条件分支 → 文案、UI预览或其他消费者。

对每条冲突判断候选解释：

- 文案与配置不属于同一快照或剧本；
- 字段含义或单位被误解；
- 字段是展示、预览或遗留数据；
- 文案过时；
- 实际结算委托服务器，客户端证据无法裁决。

不得仅凭命名相近或数值相似选择其中一个解释。

### 交付物

19条冲突台账，至少包含：冲突ID、两侧原文/原值、版本与条件、消费路径、支持与反对证据、当前结论、尚缺证据。

### 验收与停止条件

- 每条冲突给出 `resolved_within_scope`、`explained_but_runtime_unknown` 或 `unresolved`，不能静默丢弃。
- “查清为何不能裁决”也是有效交付，不要求19条全部强行选值。
- 若客户端只提供展示值，明确禁止将其当作服务器实际结算值；不把配置冲突修成无依据的统一数值。

## 6. REA-R03：数值、单位、概率和显示规则

### 优先问题

| 问题 | 要追踪的内容 |
| --- | --- |
| 发动参数100%，效果概率却45% | 发动与条件效果是否不同环节，参数分别被哪个分支读取 |
| 装备区间3.6–11与实例属性换算 | 配置展示单位与实例attrData单位是否不同，是否存在重复缩放风险 |
| weight=100 | 候选权重、筛选条件与实际随机选择分别在哪一层 |
| 79.99与80 | 浮点、截断、舍入、显示格式化的实际路径 |
| 兵书生成1–10级说明 | 文案生成能力与实际可升级等级是否分别有约束 |

### 交付物

字段语义字典：

```text
字段/namespace
原始值与原始类型
单位与缩放
转换公式或显示算法
适用版本、Scenario、等级和进阶条件
消费函数及来源位置
已验证范围
未知项与禁止外推项
```

保留raw与display两种表示；ID和64位事件整数不经过浮点中转。缺值、零值、占位和未知分开表达。

### 验收与停止条件

- 对有限代表性输入保留可复算示例，并覆盖边界值。
- 不把发动概率、条件效果概率和掉落权重压成同一个probability字段。
- 证明客户端显示算法，不等于证明服务器结算算法。
- 如实际随机函数委托服务器且本地没有相应实现，交付客户端已知约束和明确未知，不反推出不存在的概率。

## 7. REA-R04：三类高价值机制对照

### 通用要求

每个问题先列竞争解释，再选能区分解释的事件窗口。确认同一目标、同一有效窗口、实际触发，以及可能的驱散、概率失败、退场或战斗结束干扰。

UI、原始事件与客户端说明分别作为不同证据类型。没有原始事件时可以交付UI观察，但不能伪造事件序号或称为服务器内部状态观测。

### A. 清醒与控制的生命周期

已有一个“清醒先、技穷后”的UI个例。新增分析重点：

- 控制先施加，清醒后获得；
- 清醒结束时，控制仍有剩余声明时长；
- 暂时失效期间，目标是否实际成功释放主动战法。

要排除其他驱散来源、控制未发动、目标未选中等解释。普通攻击不能替代主动战法释放证据。

交付：从添加、遮蔽/暂时失效到消失/恢复的有序窗口、来源ID、剩余时长及实际行动记录。不能从现有单例推出所有清醒/控制交互，也不能把暂时失效直接称为净化。

### B. 不同来源抵御重叠

- A抵御仍有剩余次数，B抵御进入后如何变化？
- A→B与B→A是否产生不同结果？
- 随后受击消耗哪个来源，减伤与损兵记录如何对应？

交付：单来源基线、重叠前后状态、后续受击事件及不同假说能解释/不能解释的部分。

只有两个战法出现在阵容中、旧次数已耗尽或第二次作用到另一目标，都不是合格碰撞样本。

### C. 不同时长技穷重叠

- 先2回合、后1回合；
- 先1回合、后2回合；
- 从第二次命中追踪到实际到期及目标后续行动。

先回答持续时间规则，不把它混成控制强度。两种先后次序也不能自动证明相同时长不同来源的行为。

### 采样与停止条件

- 优先复用现有完整材料；如需新采样，遵守承接会话授权，另行确认客户端操作范围。
- 沿用有限选样思路，首轮最多筛选5份候选；不是要求凑满5份，更不是每类无限抓取。
- 没有符合前置条件的窗口，记为未取得合格样本；不能用不合格样本填“通过”。
- 伏兵池、满层刷新、嵌套时序列为后续问题，不在本批同时扩张。

## 8. REA-R05：采集可靠性与来源关联

### 目标

先保证一种明确页面和选定报告的获取流程可解释、可复查，而不是承诺任意战报稳定采集。

### 分析内容

- 当前页面识别与目标详情是否真正打开，定位已有主界面误拒原因。
- 客户端build、资源快照、报告ID、采集记录与解码结果之间的关联依据。
- 完整选定报告、截断报告、UI-only观察的区分。
- 采集成功、完整解码、运行来源认证三个不同状态。

### 交付物

- 小范围成功与失败案例表；失败包括导航误拒、正文未取得、选定报告不完整等真实类别。
- 每次尝试的阶段结果、停止原因、有限日志和来源绑定。
- 来源关联中哪些部分已验证、哪些只是声明或假设。

### 验收与停止条件

- 不以“进程运行了几分钟”或“输出了文件”替代目标报告取得证明。
- 原有 `real_battle_verified` 等限制只能依据新增合格证据更新，不能为了门禁变绿而改值。
- 不在交付物中保存或传播账号凭据、会话密钥等敏感材料。
- 需要新运行时操作、采集方式或权限时先说明，不由本任务书自动扩大授权。

## 9. REA-R06：地图与其他基础玩法

在首批知识闭环形成后，根据真实问答缺口选取：

- 地块等级、资源与守军配置；
- 连地、行军、占领前提及新手期差异；
- 建筑升级成本与条件；
- 章节任务判定；
- 征兵限制与资源约束。

每次只选一个子域，优先客户端有明确配置/说明、玩家经常询问的规则。动态账号状态与静态规则分开，旧观察不直接升级成所有版本规则。

交付按前述字段语义和证据格式复用，不再创建一套无法合并的知识格式。

## 10. 统一交付契约

每个任务至少交付三类文件，文件名可沿用现有工程习惯：

1. `findings.md`：结论、支持与反对证据、范围、未知、下一步。
2. `evidence-index.json`：证据ID、来源SHA、定位、类型、派生关系。
3. `rag-candidates.jsonl`：可供QA工程审核的断言候选，不是正式知识发布结果。

以下为建议字段，不声称仓库已实现该schema：

```text
candidate_id
question_id / entity_namespace / source_entity_id / variant_id
claim / raw_value / normalized_value / unit / display_value
qualifiers: snapshot, build, season?, scenario?, level?, observed_window?
evidence_kind: config | client_text | static_code | decoded_event | ui_observation
evidence_ids / source_sha256 / locator / derivation_family
conclusion_status: observed | inferred | unknown | conflicting
limitations / allowed_answer_scope / forbidden_inferences
review_state: pending
```

要求：

- 证据类型、结论性质、人工审核状态、来源认证和适用范围分别记录。
- 同一配置生成的JSON、Markdown、中文文案属于同一派生家族，不算三份独立佐证。
- 原始事件、UI观测ID、文本跨度必须保留各自定位方式。
- 每项结论能说明“RAG现在可以回答什么”和“仍不能回答什么”。
- 提供本轮实际验证命令/工具、目标SHA、有限输出与未验证范围；不复制旧大批日志充作本轮验证。

## 11. 与 QA/RAG 工程的交接边界

REA交付可复核的来源、字段语义和候选断言；QA工程负责规范化、审核流程、版本化release、检索、回答门禁与独立评测。

- 不自动把REA报告中的“已核对”转换为正式KB审核通过。
- 不自动发布候选，不让RAG调用知识发布或游戏控制工具。
- REA可以提出验收问题，但自己的推导答案不能直接被当作独立人工gold。
- 开发/测试按原始快照、实体关系族、整场battle等来源家族管理；同源派生文件不能伪装成独立样本。
- Q06a归档读取与发布继续暂停；本任务不复用其未发布材料或绕过其暂停边界。

## 12. 首批可直接派发的工作范围

> 基于已保存的NSLG资料，先完成REA-R01的首批样本版本/变体映射，再在同一明确快照上推进REA-R02缘分冲突消费路径和REA-R03数值语义核对。每项结论必须绑定来源与定位，区分观察、推断、未知和冲突，交付findings、evidence index与pending RAG candidates。客户端无法回答的服务器行为保持unknown。不要重建完整战斗引擎，不盲目增加战报采样，不自动发布知识。涉及新采样或客户端操作时，另行确认具体范围。原始证据和历史失败记录保持不变。

本任务书由技术文档工作流整理，采用REA技能的“具体问题—所需证据—有限结论—停止条件”方式组织；只新增本文档，不代表已经启动上述调查。
